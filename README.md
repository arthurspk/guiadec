## :dart: O guia para alavancar a sua carreira

> C é a linguagem criada por Dennis Ritchie em 1972 nos Laboratórios Bell e continua, mais de 50 anos depois, no núcleo de praticamente tudo que roda: o kernel do Linux, o interpretador do Python (CPython), o firmware de bilhões de dispositivos embarcados (IoT, automotivo, aeroespacial) e boa parte dos bancos de dados e servidores mais usados do mundo. Aprender C não é aprender "mais uma linguagem" — é entender como memória, ponteiros e o sistema operacional realmente funcionam por baixo de qualquer coisa que você programar depois, em qualquer stack. Este guia reúne roadmap, documentação oficial, cursos, livros, canais, ferramentas, projetos práticos e comunidades sobre C, com prioridade para conteúdo gratuito e em português. Serve tanto para quem nunca programou quanto para quem já programa em outra linguagem e quer entender o que acontece "por baixo do capô". Todo link foi verificado na data da última revisão.

## 🗺️ Roadmap

- [roadmap.sh — C Programming Roadmap](https://roadmap.sh/c) — Roteiro visual e interativo da comunidade, atualizado, com trilha por tópico e links de estudo.
- [roadmap.sh — Computer Science Roadmap](https://roadmap.sh/computer-science) — Panorama mais amplo de ciência da computação, útil para quem quer aprofundar depois de C (estruturas de dados, sistemas operacionais, redes).
- [CS50 (Harvard) — página oficial](https://cs50.harvard.edu/x/) — O curso introdutório de ciência da computação mais conhecido do mundo começa justamente em C, antes de seguir para outras linguagens.

**Trilha resumida** (siga na ordem; cada etapa tem recursos nas seções abaixo):

1. **Fundamentos** — sintaxe, tipos primitivos (`int`, `char`, `float`, `double`), operadores, entrada e saída com `printf`/`scanf`.
2. **Controle de fluxo** — `if`/`else`, `switch`, `for`, `while`, `do-while`.
3. **Funções e escopo** — passagem por valor, protótipos, recursão, variáveis locais, globais e `static`.
4. **Ponteiros e memória** — o coração da linguagem: endereços, aritmética de ponteiros, alocação dinâmica (`malloc`/`free`), e por que vazamentos e ponteiros soltos acontecem.
5. **Arrays, strings e structs** — vetores, strings como arrays de `char`, `struct`, `union`, `enum`.
6. **Arquivos e I/O** — `fopen`/`fread`/`fwrite`, streams, manipulação de arquivos binários e texto.
7. **Build e ferramentas** — compilar com `gcc`/`clang`, escrever um `Makefile`, depurar com `gdb`, encontrar bugs de memória com Valgrind e AddressSanitizer.
8. **Aplicação** — um projeto real: um interpretador simples, um shell, um servidor TCP ou firmware para um microcontrolador.

**Por onde começar:**

1. **Instale um compilador** — [GCC](https://gcc.gnu.org/) (já vem em quase toda distro Linux e via Xcode Command Line Tools no macOS) ou [Clang](https://clang.llvm.org/) — e um editor como o [Visual Studio Code](https://code.visualstudio.com/).
2. **Veja o roteiro oficial da comunidade** no [roadmap.sh — C Programming](https://roadmap.sh/c) para entender a ordem geral dos tópicos.
3. **Assista a um curso completo em vídeo:** [Curso de C — eXcript](https://www.youtube.com/playlist?list=PLesCEcYj003SwVdufCQM5FIbrOd0GG1M4) (PT-BR) ou [C Programming — Neso Academy](https://www.youtube.com/playlist?list=PLBlnK6fEyqRggZZgYpPMUxdY1CYkZtARR) (🇺🇸).
4. **Leia um livro gratuito e completo:** [Beej's Guide to C Programming](https://beej.us/guide/bgc/) ou [Modern C](https://gustedt.gitlabpages.inria.fr/modern-c/) (ambos 🇺🇸, gratuitos).
5. **Pratique todo dia** no [Compiler Explorer](https://godbolt.org/) — escreva um trecho e veja o assembly gerado — e resolva katas de C no [Codewars](https://www.codewars.com/) ou no [HackerRank](https://www.hackerrank.com/domains/c).
6. **Aprenda a depurar de verdade:** rode seus programas sob o [GDB](https://www.sourceware.org/gdb/) e sob o [Valgrind](https://valgrind.org/) para pegar vazamentos de memória antes que eles pegem você.
7. **Construa um projeto fora do tutorial:** um [interpretador de Lisp](https://buildyourownlisp.com/) ou um [shell em C](https://brennan.io/2015/01/16/write-a-shell-in-c/) do zero.
8. **Publique no GitHub** e leia a [C reference (cppreference)](https://en.cppreference.com/w/c) sempre que tiver dúvida sobre uma função da biblioteca padrão.

Seu primeiro programa em 30 segundos:

```bash
gcc --version                 # confirme que o compilador está instalado
```

```c
// ola.c
#include <stdio.h>

int main(void) {
    printf("Olá, Guia Dev Brasil!\n");
    return 0;
}
```

```bash
gcc -Wall -Wextra ola.c -o ola && ./ola   # compila (com avisos ligados) e executa
```

## 📖 Documentação oficial

- [C reference (cppreference.com)](https://en.cppreference.com/w/c) — Referência completa e community-maintained da linguagem e da biblioteca padrão, com exemplos executáveis.
- [C23 — página de referência (cppreference)](https://en.cppreference.com/w/c/23) — Tudo que mudou na revisão mais recente do padrão da linguagem.
- [ISO/IEC 9899:2023 (C23) — draft público (WG14 N3220)](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n3220.pdf) — O texto de trabalho mais próximo do padrão oficial C23, publicado pelo comitê ISO.
- [WG14 — comitê da linguagem C (ISO)](https://www.open-std.org/jtc1/sc22/wg14/) — Site oficial do grupo de trabalho que define o padrão da linguagem C.
- [GNU C Library — manual (glibc)](https://sourceware.org/glibc/manual/latest/html_node/) — Documentação oficial da implementação da biblioteca padrão C usada pela maioria das distros Linux.
- [GCC — documentação oficial](https://gcc.gnu.org/onlinedocs/) — Manuais completos do GNU Compiler Collection, incluindo todas as flags de compilação e avisos.
- [GCC 15 — notas de versão](https://gcc.gnu.org/gcc-15/changes.html) — O que mudou na versão mais recente do GCC, lançada em 2025.
- [Clang — documentação oficial](https://clang.llvm.org/docs/) — Documentação do compilador da LLVM, incluindo diagnósticos, sanitizers e extensões.
- [Clang — notas de versão](https://clang.llvm.org/docs/ReleaseNotes.html) — Mudanças da versão mais recente do Clang.
- [LLVM — releases](https://releases.llvm.org/) — Página oficial com todas as versões da LLVM/Clang, incluindo os lançamentos de 2024 a 2026.
- [Wikibooks — C Programming](https://en.wikibooks.org/wiki/C_Programming) — Livro-texto colaborativo e gratuito, bom complemento à referência oficial.
- [Linux man-pages — seção 3 (funções de biblioteca)](https://man7.org/linux/man-pages/dir_section_3.html) — Referência oficial de todas as funções da biblioteca C no Linux, acessível também via `man 3 <função>`.
- [GDB — documentação oficial](https://sourceware.org/gdb/documentation/) — Manual completo do depurador padrão do ecossistema GNU/Linux.
- [The GNU Make Book / guia de referência (Paul D. Smith)](https://make.mad-scientist.net/) — Guia de referência do GNU Make mantido por um de seus ex-mantenedores oficiais.
- [GNU Make — projeto oficial (Savannah)](https://savannah.gnu.org/projects/make/) — Página oficial do projeto GNU Make no Savannah, com links para releases e manual.
- [C language reference (Microsoft/MSVC)](https://learn.microsoft.com/en-us/cpp/c-language/c-language-reference) — Referência oficial da Microsoft para o compilador C do Visual Studio, útil para quem desenvolve no Windows.
- [comp.lang.c FAQ](http://c-faq.com/) — FAQ clássico e ainda muito citado sobre armadilhas comuns da linguagem C.
- [POSIX.1-2024 (The Open Group Base Specifications)](https://pubs.opengroup.org/onlinepubs/9799919799/) — Especificação oficial do POSIX, base das APIs de sistema (arquivos, processos, threads) usadas em C no Linux/Unix.
- [Valgrind — manual oficial](https://valgrind.org/docs/manual/manual.html) — Documentação completa da suíte de ferramentas de análise dinâmica de memória.
- [AddressSanitizer — wiki oficial](https://github.com/google/sanitizers/wiki/AddressSanitizer) — Documentação do sanitizer mais usado para achar bugs de memória em tempo de execução.

## 🛠️ Ferramentas

- [GCC](https://gcc.gnu.org/) — O compilador C mais usado no mundo Linux/Unix, open source e mantido pelo projeto GNU.
- [Clang / LLVM](https://clang.llvm.org/) — Compilador moderno, com mensagens de erro mais claras e diagnósticos avançados.
- [GDB](https://www.sourceware.org/gdb/) — O depurador padrão do ecossistema GNU, essencial para investigar crashes e comportamento inesperado.
- [LLDB](https://lldb.llvm.org/) — Depurador do projeto LLVM, usado por padrão no macOS e integrado a vários editores.
- [Valgrind](https://valgrind.org/) — Suíte de ferramentas para achar vazamentos de memória e erros de acesso em tempo de execução.
- [GNU Make](https://savannah.gnu.org/projects/make/) — A ferramenta de build mais tradicional para projetos em C.
- [CMake](https://cmake.org/) — Gerador de builds multiplataforma, hoje padrão de mercado para projetos C/C++ maiores.
- [Ninja](https://ninja-build.org/) — Sistema de build focado em velocidade, muito usado como backend do CMake.
- [Compiler Explorer (Godbolt)](https://godbolt.org/) — Playground online que mostra o assembly gerado pelo seu código C em dezenas de compiladores.
- [Cppcheck](https://cppcheck.sourceforge.io/) — Ferramenta de análise estática focada em encontrar bugs reais com poucos falsos positivos.
- [clang-tidy](https://clang.llvm.org/extra/clang-tidy/) — Linter e ferramenta de refatoração baseada no Clang.
- [clang-format](https://clang.llvm.org/docs/ClangFormat.html) — Formatador de código automático, configurável por projeto.
- [Visual Studio Code](https://code.visualstudio.com/) — Editor leve e gratuito, com boas extensões para C.

## 🤖 IA na prática

C é a linguagem em que a IA mais erra de forma silenciosa: um `malloc` sem `free`, um `strcpy` sem checar tamanho ou um ponteiro solto (*dangling pointer*) compilam sem nenhum aviso e só quebram em produção. Use a IA como tutora e revisora — nunca como verificadora de memória; essa função é do compilador com avisos ligados e das ferramentas de análise abaixo.

**Para aprender**
- Cole um erro de compilação ou um `Segmentation fault` junto com o trecho de código e peça: *"explique por que esse ponteiro é inválido e mostre como corrigir"*.
- Peça para explicar um conceito com um exemplo executável — aritmética de ponteiros, alocação dinâmica, structs com ponteiros — e rode o exemplo no [Compiler Explorer](https://godbolt.org/) para ver o assembly gerado.
- Peça **exercícios com gabarito** sobre o tópico que está estudando (ponteiros, arrays, structs) e resolva antes de olhar a resposta.
- Peça para reescrever um trecho seu de C "estilo antigo" (K&R) usando recursos mais modernos (C11/C17/C23: `stdbool.h`, `_Generic`, inicializadores compostos) e explicar cada mudança.

**Para trabalhar**
- Use o [GitHub Copilot](https://docs.github.com/pt/copilot), o [Cursor](https://cursor.com/) ou o [Claude Code](https://code.claude.com/docs/en/overview) para escrever testes, gerar `Makefile`s e revisar pull requests — mas trate toda sugestão envolvendo ponteiros e alocação de memória como não confiável até provar o contrário.
- Depois de **cada** sugestão aceita, compile com `-Wall -Wextra -fsanitize=address,undefined` e rode o binário sob o [Valgrind](https://valgrind.org/) ou o [Cppcheck](https://cppcheck.sourceforge.io/). Se o código só "funciona" sem essas flags, provavelmente há undefined behavior escondido.
- Peça sempre o padrão-alvo ("C17", "C23", "compatível com C89 para embarcados") — sem isso a IA mistura sintaxes de décadas diferentes na mesma resposta.

**Limites e boas práticas**
- A IA **inventa funções e comportamentos de biblioteca** que não existem, ou confunde `sizeof` aplicado a um ponteiro com `sizeof` aplicado a um array. Confirme sempre na [C reference (cppreference)](https://en.cppreference.com/w/c) ou no `man`.
- Ela erra sistematicamente sobre **undefined behavior**: overflow de inteiro com sinal, dupla liberação de memória (*double free*), *use-after-free* e estouro de buffer aparecem em sugestões com aparência perfeitamente válida.
- Nunca aceite código gerado que desabilite avisos do compilador (`-w`) ou substitua checagem de limites por "confia".
- Não cole código proprietário, segredos ou dados de clientes em ferramentas de IA sem a política da sua empresa.
- Entenda o que você aceita: em C, um bug de memória vira vulnerabilidade de segurança com mais facilidade do que em qualquer outra linguagem popular.
